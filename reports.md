# Reports Page — Specification & Work History

This document captures what the **Reports** section of the Ooredoo POS admin dashboard should provide, the data model behind it, and the chronological history of changes that led to the current state.

---

## 1. Purpose

The reports page is the admin's window into business performance. It must answer three questions at a glance:

1. **What happened today?** — live, end-of-day numbers per store
2. **What happened over time?** — trends by week, month, and store
3. **Where can I drill down?** — full session, sale, void, and audit history for any past day

All monetary values are in Algerian Dinar (DZD).

---

## 2. What the page should have

### 2.1 Generate end-of-day report (existing)

- One-click "Generate today's report" button (admin-only).
- Refuses to generate if any cashier session is still **open** for that day.
- Refuses to regenerate if a report for that store/date already exists (one report per store per day, enforced by `daily_reports.UNIQUE (report_date, store_id)`).
- Records who generated the report and when, in `audit_logs` with action `REPORT_GENERATE`.
- Generates **one row per store** (AAO Sobha, Kiosque Ain Meraine), not a single combined row.

### 2.2 Reports list (existing, needs polish)

A sortable, paginated table of past reports with:

| Column | Source |
|---|---|
| Date | `report_date` |
| Store | join on `stores.name` |
| Generated by | join on `users.username` |
| SIM units sold | `total_sim_units` |
| Total revenue | `total_selling_price + total_storm + total_accessories` |
| Gross profit | `gross_profit` (computed) |
| Total commissions | `total_commissions` |
| Total debts | `total_debts` |
| Actions | View / Export PDF / Export CSV |

**Filters:**
- Date range picker (default: last 30 days)
- Store selector (All / AAO Sobha / Kiosque Ain Meraine)
- Generated-by user

### 2.3 Report detail view (partial — improve)

Modal or dedicated page showing the full snapshot for a single (store, date) pair:

**Top KPI cards:**
- Total revenue (SIM + Storm + Accessories)
- Real cost (sum of `real_price_snapshot`)
- Gross profit
- Total commissions paid to cashiers
- Total debts issued
- Net cash movement (revenue − debts)

**Session-by-session breakdown:**
- One card per cashier session that day showing:
  - Cashier name, store, opening cash
  - SIM units sold, total selling price, total cost, points generated
  - Storm total, accessories total, debt total
  - Cashier benefit (commissions earned)
  - Expected register cash at close
  - List of any voided transactions with reason

**Stock movement:**
- SIM cards consumed during the day with their serial numbers and which offer was applied at sale time
- Accessories sold per category

**Pool & register state at end of day:**
- Global pool (`balance`, `bonus`, `points`) latest values
- Each store's register cash latest values

**Export:**
- PDF (printable)
- CSV (raw data for accounting)

### 2.4 Trends & analytics (new — to build)

A separate "Analytics" tab inside the reports section showing aggregations over time:

**Charts:**
- Daily revenue over the last 30 days (line chart, one series per store)
- SIM units sold per day (bar chart, stacked by offer)
- Gross profit margin trend (revenue − cost − commissions, percentage)
- Top 5 best-selling SIM offers this month
- Top 5 best-selling accessories this month
- Cashier leaderboard (commissions earned this month)

**Month-over-month KPIs:**
- This month vs last month: revenue, profit, SIM units, debts
- Driven by `v_monthly_summary` view

### 2.5 Audit log viewer (new — to build)

A searchable, paginated view of `audit_logs` so admin can answer "who did what":

- Filter by user, action type (LOGIN / VOID / STOCK_ASSIGN / etc.), date range, table
- Show the JSON diff between `old_values` and `new_values`
- Useful for investigating discrepancies

### 2.6 Cashier history (new — to build)

For a selected cashier:
- All their sessions over a date range with totals
- Total commissions earned per month
- Voided transaction count and reasons
- Inventory snapshots: how many SIMs assigned vs sold

## 4. Data model

The reports rely on these tables and views (all already exist):

- **`daily_reports`** — immutable end-of-day snapshot per store per day. JSONB `snapshot` column holds the full picture.
- **`v_session_live_totals`** — live per-session aggregates (used during the day, frozen into snapshots at report time).
- **`v_monthly_summary`** — pre-aggregated KPIs per store per month from past reports.
- **`audit_logs`** — append-only log of every mutation, login, void, session open/close.
- **`global_pool_state`**, **`store_register_state`** — append-only logs; "current" state is the latest row per scope.

Daily report structure (the JSONB `snapshot`):

```jsonc
{
  "sessions": [
    {
      "session_id": 31,
      "cashier_id": 2,
      "cashier_name": "Aymen",
      "store_id": 1,
      "store_name": "AAO Sobha",
      "opening_cash": 5000,
      "sim_units_sold": 12,
      "sim_total_real_price": 16800,
      "sim_total_selling_price": 18000,
      "sim_total_points": 1800,
      "sim_total_commission": 600,
      "storm_total": 4500,
      "accessories_total": 12000,
      "accessories_total_commission": 200,
      "debt_total": 1500,
      "expected_register_cash": 38000,
      "total_cashier_benefit": 800,
      "voided_transactions": [
        { "type": "sim", "id": 312, "reason": "Wrong offer", "amount": 1500 }
      ]
    }
  ],
  "global_pool": {
    "available_balance": 250000,
    "available_bonus": 12000,
    "available_points": 4500
  },
  "register": {
    "cash_amount": 38000
  }
}
```

## 5. Work history

Chronological log of changes that have touched (or directly affect) the reporting feature.

### 2026-05-04 — Initial schema
- Defined `daily_reports`, `v_session_live_totals`, `v_monthly_summary`, `audit_logs` in `database/schema.sql`.
- Added immutability trigger on `daily_reports` (cannot UPDATE or DELETE once generated).
- Stub `reportsController.js` and `reportsRoutes.js` created.

### 2026-05-04 — First implementation
- `POST /api/reports/generate` writes one row per store per day with pre-computed totals + JSONB snapshot.
- `GET /api/reports` returns the last 50 reports joined with store and generator names.
- Frontend `DailyReports.jsx` lists reports and shows a basic detail modal.

### 2026-05-11 — Critical bug fixes (deployment audit)
- **Fixed** `generateDailyReport` querying non-existent columns:
  - `SELECT balance, bonus, points FROM global_pool_state` → corrected to `available_balance, available_bonus, available_points`.
  - `SELECT current_cash FROM stores` → corrected to `cash_amount FROM store_register_state ORDER BY id DESC LIMIT 1`.
- These bugs would have made every report-generation attempt fail in production.

### 2026-05-11 — Audit & observability
- Every report generation now logs to `audit_logs` with `REPORT_GENERATE` action.
- `errorHandler` middleware forwards 5xx errors to Sentry (when `SENTRY_DSN` is set).
- `pino-http` request logger captures every report API call with response time.

### 2026-05-14 — SIM inventory rework
- Switched from session-scoped quota to physical-card model (`sim_cards` table with serial numbers).
- Reports now have access to per-serial sales data via `session_sim_sales.serial_number_snapshot` — future detail view should show serials sold per cashier per day.
- `v_sim_stock_remaining` removed; `v_cashier_sim_inventory` added (per cashier totals).

### 2026-05-14 — Generic SIM cards
- `sim_cards` no longer carry an `offer_id` at assignment. Offer is decided at sale time and snapshotted on the sale row.
- Reports already work because they aggregate from `session_sim_sales` (which has the offer snapshot), not from the inventory table.

### 2026-05-14 — Generate v2: live preview, force-close, rich snapshot
- New `GET /api/reports/preview?date=` endpoint shows what would be generated before clicking the button: closed/open session counts, per-store totals, and which stores already have a report on that date.
- `POST /api/reports/generate` now:
  - Refuses to generate if any session is still open (returns `409 OPEN_SESSIONS_BLOCKING` with the cashier names) unless `force_close_open_sessions: true` is passed in the body.
  - Refuses to generate for a future date (`400 FUTURE_DATE`).
  - Logs every generation (and every force-closed session) to `audit_logs` with `REPORT_GENERATE` / `SESSION_CLOSE`.
  - Embeds full **line-item detail** into the JSONB snapshot: every SIM sale (with serial number), every storm entry, accessory sale, and debt — including voids and void reasons. Old reports remain readable; the UI is tolerant of the older snapshot shape.
- New `GET /api/reports/:id` for full snapshot retrieval.
- `GET /api/reports` accepts `from`, `to`, `store_id`, `limit`, `offset`.
- All list/detail responses include computed `total_revenue` and `margin_pct` so the frontend doesn't have to reconstruct them.
- **Fixed** field-name mismatch: the UI used to read non-existent `total_revenue` / `total_profit` columns and showed empty cells. Now driven by the controller-decorated response.
- New `DailyReports.jsx` UI:
  - Date picker (capped at today) to pick any past or current date.
  - Live preview panel: KPI tiles, per-store cards (Generated / Ready / No closed sessions), open-session warning with cashier names.
  - Generate button is disabled until at least one store is "Ready". If open sessions block generation, the UI surfaces the conflict message and offers to force-close them.
  - Past-reports table now shows: SIM units, revenue, profit, margin %, debts, generator name.
  - Detail modal: top KPIs (revenue, cost, profit + margin, commissions, SIM/Storm/Accessories/Debts), pool & register snapshot, expandable per-session cards with full line-item tables (serials, offers, prices, void status with reasons).

## 7. Acceptance criteria for "Reports v2"

The reports section is complete when:

- [x] An admin can generate a daily report for any past date (not just today).
- [x] Reports are listable, filterable, and paginated.
- [x] Each report opens a full detail view with session-by-session breakdown.
- [ ] Reports can be exported as PDF and CSV.
- [ ] An analytics tab shows the four core charts (daily revenue, SIM units, top offers, cashier leaderboard).
- [ ] An audit log viewer is reachable from the reports section.
- [x] All endpoints are admin-only and instrumented with audit logging.
- [x] Reports continue to render correctly even when referenced cashiers/products have been deleted.
